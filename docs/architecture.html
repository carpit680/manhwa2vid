manhwa recap pipeline · architecture reference

How manhwa2vid turns scanlation pages into a narrated recap video

Nine stages, each reading and writing files on disk. No stage passes data to the next in memory — the artifact contract on disk is the interface, which is what makes any stage independently re-runnable, cacheable, and gate-able.

Sections marked changed cover work that reversed an earlier design decision. Three of those reversals matter more than everything else here: perception became whole-chapter, narration became a single pass, and every rule the model kept declining moved into a deterministic polish pass.

The end-to-end flow

Every stage reads its inputs from JSON/PNG on disk, writes its outputs, and appends itself to checkpoint.json. A stage that finds its own output file already present prints "Using cached …" and returns; --force re-runs it and explicitly deletes anything downstream that its new output would falsify.

What each stage actually does

01 ingest
ingest/

Normalizes either a folder of scanlation images or a PDF into uniform page PNGs at a fixed width.

reads
source images / PDF
writes
pages/*.png, pages/manifest.json
02 panels
panels/split.py

Three modes for image projects: one_to_one, always_split (gutter detection via row-ink density), and hybrid. PDFs always gutter-split. Each panel is stamped with ink_ratio and dark_ratio — the pixel stats that later let blank page-transition slivers be excluded before they cost vision tokens or get rendered as blank screen time.

reads
pages/manifest.json
writes
panels.json, panels/*.png, debug/ overlays
03 scout
characters/scout.py

Samples panels from later chapters through the vision model, so the character bible already knows a character before this chapter's narration needs to name them. This is why a recap can use a name in beat 3 rather than "an orange-haired woman".

reads
lookahead chapter images
writes
series/character_bible.json, series/scout/
04 ocr+scene
ocr/extract.py

The vision pass, and the most consequential stage. changed It now runs in two passes over the whole chapter rather than panel by panel.

Pass 1 — chapter read. One call sees the chapter and returns a story map: a summary, the cast roster with the features that identify each person, any temporal device, last_flashforward_panel, and return_to_present_line. Panel-at-a-time perception could never answer "is this a flashback?" because the answer is not inside any one panel.

Pass 2 — labeled windows. Panels are annotated in windows of ~12, with a text label interleaved before each image (describe_labeled_panels), so panel binding is positional rather than a count the model has to maintain. Before that, identifications drifted by a fixed offset — every card described the panel three along.

Speech bubbles are captured as objects — {text, speaker, to} — so who says it and to whom is judged where bubble tails and gaze are actually visible, not guessed downstream from a paraphrase.

reads
panels.json, character_bible.json, corrections.json
writes
scene_cards.json, ocr.json, panels.story.json, scene_story_map.json
gates
cards-coverage, speakers-visible, dialogue-grounding, identification-basis
05 cast
characters/link.py

Per-chapter identity pass: heuristic descriptor merges plus one LLM merge pass, then writes panel → people attribution. Any ref that doesn't exist in the bible is resolved or seeded — never left dangling. Generic refs (char_bystander and friends) are re-resolved against named cast that has already appeared face-on.

reads
scene_cards.json, character_bible.json
writes
cast_attribution.json, scene_cards.enriched.json
gates
referential-integrity, no-merged-refs, protagonist-exists
06 script
script/generate.py

Synopsis, then a deterministically seeded outline, then one narration call for the whole chapter changed, then lint/rewrite, an adversarial alignment audit, and finally the deterministic polish pass. Two dedicated sections below cover this; it is where most of the quality lives.

reads
enriched cards, attribution, bible, story map
writes
script.synopsis/outline/json, script.draft.md, debug/storyboard.html
gates
beat-conservation, panel-conservation, beat-panel-balance, narration-complete, alignment, style
07 tts
tts/engine.py

Synthesizes one WAV per beat (Kokoro, am_adam), then splits each beat's audio across its panels so durations sum exactly to the audio length. Min/max panel seconds are best-effort and yield to A/V lock.

Per-panel clips (scroll for tall webtoon strips, Ken Burns otherwise) → concat → mix narration and optional BGM → loudnorm.

export/

writes

Inside the script stage: structure is decided in code, wording in one pass

Two failure modes shaped this stage, and they pull in opposite directions. Ask a model to write beats freely over a chapter's panels and it narrates a later scene over early panels. Constrain it too tightly — hand it five beats at a time — and it repeats itself, because no single call ever sees the whole chapter. The resolution: panel bindings are decided deterministically before any wording exists, and then all the wording is written in one call.

Why narration is ONE call changed

Narration used to run in chunks of five beats. Each chunk was an independent sample, so beat 17 could not know beat 18 was about to narrate the same gate entrance, and the 180-character running_summary digest was far too thin to stand in for having actually written the earlier beats.

The hand-checked gold script was produced in one pass over the whole chapter, which is exactly why it never repeats a moment. Switching to narration_chunk_size: 0 fixed three observed defects at once: a character no longer asks to lead after being described as already chosen, the last two beats progress instead of both entering the gate, and the closing beat became concrete.

Why beats must be contiguous

A real outline produced these two beats:

beat 10: p0017_01, p0018_02, p0018_03
beat 11: p0017_02, p0018_04

Reading order is 17_01, 17_02, 18_02, 18_03, 18_04 — so beat 11 narrated a character asking for coffee after beat 10 had already walked him away from the stall, and both beats narrated the refusal. Two beats handed overlapping stretches of one moment will both tell it, however the prompt is worded. No amount of whole-chapter context repairs a bad partition, which is why the repair is structural and runs before any wording exists.

The deterministic polish pass changed

The governing rule of this codebase: prompts set voice and judgment; code enforces invariants. When the model declines the same rule twice, that rule stops being a request and becomes a function. The polish pass runs after every LLM stage — after lint rewrites, after the alignment audit — and nothing may generate text after it.

FunctionThe defect it makes impossible
strip_repeated_appositives A character re-introduced every time they appear. Eleven beats were flagged across two runs and the rewrite complied zero times.
strip_appearance_descriptors People identified by clothing — "a hunter with a fur collar and another in a green jacket". Also trims a named character's intro clause down to their role, which is the format the style target actually uses.
strip_caption_sentences Sentences that read as image alt-text rather than events.
strip_duplicate_transitions A chapter rewinding from its flashforward three times, because the prompt rule fires per beat.
lock_transition_line The return to the present rewritten into worse English than the exemplar it was given. Placement and wording are both fixed now; the wording comes from the chapter read, so it is per-chapter, not hardcoded.
repair_malformed_openings A beat that starts mid-clause on a lowercase fragment.
repair_truncated_sentences Narration ending on a dangling function word. A bubble that runs across a panel border is captured as a fragment, and the writer reproduces the cut — which TTS then reads into silence. A copula tail is preserved, because that form is the manhwa's own cliffhanger.
strip_internal_labels Script-writing vocabulary in the narrator's mouth. The prompt allowed "the protagonist" once as a pressure valve and the model spent it on the opening line.
dedupe_intra_beat_sentences One beat stating the same thing two or three ways.
dedupe_cross_beat_sentences A beat restating what an earlier beat already told. Works at sentence level because the beat is the wrong unit — two beats retelling one exchange while differing elsewhere score below any whole-beat threshold.
fix_pronoun_case Both directions of pronoun corruption: an object pronoun where a subject belongs, and the reverse.
enforce_mc_name_budget The protagonist carried as "he" for fifteen straight beats, or named in every sentence. Cadence-based, and an ambiguous beat forces an anchor.

A bug here ships on every run

That is the cost of this design, and it has been paid three times. One version of the appearance strip consumed only the first garment phrase and left "a supporting hunter and grey hair" in the draft. The appositive stripper required a trailing comma, so an appositive that ended a sentence survived. Read the polish output directly — do not trust the diff.

State a check's limits instead of tuning it until it fires

dedupe_cross_beat_sentences catches near-verbatim restatement at 0.6 token overlap. The observed coffee repetition scores 0.29 — the two sentences share almost nothing lexically. A threshold low enough to catch it would start deleting correct sentences, so paraphrased repetition is deliberately left to the style gate and a human edit. A test pins that limit so nobody lowers the threshold later without seeing why it sits where it does.

Character identity — roughly half the codebase

A vision model describes each panel independently, so the same person arrives as three different descriptions and one name. Collapsing those into one stable id is what makes narration readable. The bible is not a static input — it is a store each pass writes back into, and that feeds the very prompts producing the next identification.

The reference window is disabled by default

Leading each vision request with pictures of the cast is intuitively right and measured wrong. With the window on, injury-in-action claims appeared in 85% of panels against 7% without it: the "reference" was itself a scroll strip carrying its own bubbles and action, and the model narrated the reference instead of the panel. The rolling multi-image window and confidence gating are implemented and available, but off unless deliberately enabled — kept because the underlying idea (anchor identity to pixels, spread across chapters, high-confidence images only) is sound and the failure was in what got passed as a reference.

What makes it work on a different title changed

The pipeline was developed against one series, and a set of that series' facts had settled into the code. Most did not fail loudly on another title — they simply stopped doing anything, which is worse. Everything below now derives from per-project data you control: the hand-editable glossary.json, the series bible built from it, or the chapter read.

Was hardcodedNow derived fromWhat it would have done to a new series

wiki fallback roster nothing — glossary is the source Any failed wiki lookup seeded the development series' cast into a different title's bible.
grounding keywords glossary "terms", else config, else empty Narration was checked against one series' props; another title's vocabulary was ungoverned.

The guard

tests/test_series_agnostic.py drives a completely different series through identity, grounding and prompt construction, and parametrizes a scan over every prompt string the pipeline ships. A development-series name reappearing in model-facing text fails the build. Comments and docstrings are exempt by design — they record why each rule exists, and never reach a model.

Derivation is harder than it looks

Two drafts of the signal derivation were worse than the hardcoded list before tests caught them. One admitted stopwords, making "with" a signal that matched every reference. Another took tokens from polluted aliases, making a colour word a signal that then matched a different character's jacket. Names contribute their tokens; longer descriptors contribute only n-grams whose every word is distinctive.

QA gates — nothing fails silently

Each gate encodes a bug that actually shipped once. A gate is pass, warn, or fail; a fail blocks the next stage unless --force-past-qa is passed. tests/test_qa_gates.py holds one regression fixture per observed bug — a new failure class gets a gate and a fixture.

Green gates are not a review

A run has shipped with every gate green and five real defects in the text: a gesture read backwards, a garbled causal clause, a self-contradicting beat, two beats entering the same gate, and a sentence that said nothing. Gates measure what has already been learned to look for. Every defect found in the last stretch of work was found by reading the script, never by a metric — the metrics' job is to catch regressions of known failures, and they are good at exactly that and nothing more.

Providers, config, and the two directory scopes

Per-stage model selection

Vision and text stages resolve independently, in order: {STAGE}_LLM_PROVIDER env → LLM_PROVIDER=mock kill-switch → config[stage].provider → global default. The model pin is applied only when no env override redirected the provider — otherwise one vendor's model name lands on another vendor's client.

Model availability is key-dependent and changes without notice; a lineup that worked last month can 404 today. Verify with tools/vision_bakeoff.py --list rather than trusting a name in config.

Two ways a run can lie to you

A missing API key downgrades to MockLLMProvider with only a warning, so a real run completes and writes a placeholder script. If a script looks nonsensical, check for that warning first. An invalid key behaves differently — it fails loudly mid-stage with a 401.

Exhausted billing used to be worse: three consecutive runs reported success with green gates while doing nothing. BillingExhausted is now a fatal, never-retried error, preflight_check runs before a stage spends time, and a vision pass that produces zero cards raises instead of returning quietly.

Project vs. series directory

A project is one recap over one chapter range: projects/<title>-ch<range>/. A series is shared across all projects of that title: projects/<title>/series/ holds the character bible, quest state, scout samples, and the reference window. That split is how sticky names and identity survive between chapters.

Reference style target

Narration is tuned to statistics measured from the channel being imitated: 237 WPM, ~12.8-word sentences, a reported-speech verb every ~32 words, near-zero first person and slang, present tense. Several config.yaml values trace directly to those numbers — change them together and re-measure with reference/profile_srt.py rather than guessing.

Before review, open the storyboard

debug/storyboard.html puts each beat's narration next to the actual panels it will play over. It is the fastest way to catch the class of error no gate has been written for yet.

When you approve a panel reading, write it down

Vision is non-deterministic. A gesture read correctly on one run comes back wrong on the next, so without corrections.json every reviewer-approved fix is a fresh coin-flip on the following run — the same note gets reported twice. Add an entry the moment a reading is signed off; it is applied on every card load thereafter.
